# Optional shared request quotas

By default, each server still uses its bounded in-memory rate limiter. To share quotas between processes on one host, configure `RATE_LIMIT_DB_PATH` to a dedicated local SQLite file and `RATE_LIMIT_KEY` to the same protected 64-character hexadecimal secret in every process. The parent directory must already exist. No service is enabled or restarted automatically.

The database must be separate from evidence, jobs and metrics. Unrelated tables, unsupported metadata, a mismatched key or conflicting family rules reject initialization. The three existing families retain their limits: v1 120/minute, admin 60/minute, static 240/minute. Readiness bypasses quota enforcement. Trusted proxy configuration still determines client identity.

Each request uses an immediate SQLite transaction to prune expired identities, inspect the shared counter and increment it atomically. Per-family capacity is 10,000 active identities. New identities are denied at capacity without resetting existing quotas. Blocking does not extend expiry. Requests across processes and restarts consume the same counter. Lock contention waits up to 100 ms; errors return sanitized HTTP 503 rather than bypassing enforcement. Readiness returns `quota_unavailable` when its database read fails; a successful readiness read does not guarantee a subsequent write lock will be available.

Client identifiers are stored as keyed HMAC-SHA256 values, not raw IP addresses. These remain pseudonymous data, not anonymous data. Expired rows are removed lazily on the next request in their family; idle databases can retain them indefinitely and SQLite pages/WAL can retain deleted values. Protect filesystem and key access. No request text or credentials are stored in quota rows. Closing the store wipes its private key buffer; the application's environment remains operator-managed.

This is same-host coordination, not multi-host distributed rate limiting. Use local storage; SQLite WAL on network filesystems is not supported by this design. All processes must share a stable wall clock, key, path and matching rules. Clock jumps affect window length. To rotate a key or change rules, stop all participating processes and explicitly provision a new dedicated database; this resets active quotas. Online rotation and multi-host backends remain open. Separate databases or keys do not combine quotas. Synchronous SQLite writes add latency; measure the intended workload before rollout. The default in-memory limiter remains preferable when shared coordination is unnecessary.

Validation uses temporary databases, independent worker threads, separate HTTP servers, restart and expiry tests, capacity tests, mismatched configuration, write-lock contention and unavailable-store responses. No live deployment or multi-host throughput claim is made.
